## 5. 基准测试结果（性能冒烟，对照文档 01 §5 / 08 §6）

环境：Windows 11 / Intel i7-9750H 2.60GHz / Go 1.26.5 / SQLite WAL（单连接）

### 5.1 HTTP 与配置层

| Benchmark | 结果 | 说明 |
|-----------|------|------|
| Healthz | 3.74 µs/op | 完整中间件链 + healthz |
| UnknownAPI404 | 4.24 µs/op | 中间件链 + JSON 失败响应（M2 起失败分支同路径） |
| ConfigParse | 4.77 µs/op | 启动配置解析 |

### 5.2 SQLite 数据层

| Benchmark | 结果 | 说明 |
|-----------|------|------|
| AuthLookup | 45.8 µs/op | 认证核心 JOIN 查询（文档 03 §3，走索引） |
| KeyInsert | 1.87 ms/op | 密钥写入（含索引更新） |
| AuditInsert | 1.85 ms/op | 单条审计写入（含 fsync） |

### 5.3 服务层

| Benchmark | 结果 | 说明 |
|-----------|------|------|
| Argon2Hash | 98.7 ms/op | argon2id（64MB/3 轮/2 并行）——admin 初始化一次性成本 |
| RandomString30 | 337 ns/op | 30 位随机密码生成 |
| EnsureAdminExisting | 55.9 µs/op | 幂等检查路径（每次启动执行） |
| EnsureAdminFirstRun | 115 ms/op | 首次初始化完整成本（哈希 + 写库 + auth.log） |

### 5.4 性能预算分析（为 M2/M3 认证接口预留）

目标（文档 01 §5）：认证接口 **P99 < 50ms、≥ 100 QPS**；管理接口 P99 < 100ms。

M1 实测组件开销 → 认证接口（M3）主路径估算：

```
AuthLookup 45.8µs + AuditInsert 1.85ms + HTTP/JSON ~10µs ≈ 1.9ms / 请求
```

- **延迟**：1.9ms 远低于 50ms 预算（余量约 26×），P99 达标无风险。
- **吞吐**：SQLite 单写者 + 单连接串行化，写路径瓶颈在审计写入（1.85ms）→ 理论上限约 **540 QPS**，超过 100 QPS 目标 5 倍。若认证接口高频调用导致审计写成为瓶颈，可复用文档 04 §7 的「last_used_at 60s 窗口低频更新」与审计异步化策略。
- **启动自检**：首次初始化 115ms（argon2 占 98.7ms），仅首次发生；重启幂等路径 55.9µs，可忽略。
- **结论**：M1 骨架性能余量充足，M2/M3 按文档既定方案实现即可达标。
