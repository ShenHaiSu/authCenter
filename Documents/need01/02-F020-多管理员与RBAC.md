# 02 F-020 多管理员与 RBAC —— 施工设计

> need01 / 2 ｜ 里程碑 **M9** ｜ 依赖：`internal/database/migrate.go`（《05》§4 幂等 ALTER 规范，F-021 会共用）｜ 风险：中（改会话归属解析）
> 上游：需求 F-020「多管理员与 RBAC：admin 支持新增/停用，角色预留（预留 `role` 字段，不做复杂权限）」

## 1. 目标与非目标

**目标**
1. 支持新增多个管理员账号，可单独停用/启用，停用即刻失效其全部会话。
2. 引入**两角色**：`owner`（超级管理员）/ `admin`（管理员），预留 `role` 字段以便未来扩展。
3. 系统始终至少存在一个启用的 `owner`（防把自己锁在门外）。
4. owner 可重置他人密码，并可要求对方下次登录强制改密。
5. 所有管理动作可追责到具体管理员（审计 `actor_id` 已是 id，此设计使之真正有意义）。

**非目标（明确不做）**
- 不做细粒度权限矩阵（项目/密钥/审计按角色分权）——两角色除「管理员账号管理」外权限相同。
- 不做只读角色 `viewer`（列 P3，预留 `role` 值空间即可）。
- 不做管理员自助注册/邀请邮件/组织架构（无公网场景）。
- 不做管理员操作自己账号以外的密码读取（任何角色都无法查看他人密码哈希）。

## 2. 现状与关键缺口（含一处必须修正的硬编码）

| 项 | 现状 | 缺口 |
|----|------|------|
| `admin_user` 表 | `id/username/password_hash/is_active/created_at/last_login_at/last_login_ip` | **无 `role`、无 `force_password_change`、无 `updated_at`** |
| 账号创建 | 仅 `AdminService.EnsureAdmin` 启动时创建 `admin`（幂等） | 无管理端创建路径 |
| 会话 | `admin_session.admin_user_id` **已正确记录归属** | — |
| 登录 | `SessionService.Login` 按 `username` 取人 + IP/用户名双维度限流 | 已天然支持多用户，无需改造限流 |
| 改密 | `ChangePassword` 只能改自己（需旧密码） | 无 owner 重置他人路径 |
| 停用 | `is_active` 字段存在，`Login` 已校验 | 无管理端入口，无「停用即吊销会话」 |
| **鉴权中间件** | `RequireAdmin` 中 `user, err := st.GetAdminByUsername(r.Context(), "admin")` | **硬编码用户名 `admin`**：多账号下所有会话都会被解析成 `admin` 这一个用户，`is_active`/角色判断全部失真 → **本设计的必改项** |
| 前端 | 顶栏显示 `me.user.username` | 无角色概念、无管理员管理视图 |

> **必改项 P0**：`middleware.go:136` 必须改为按 `sess.AdminUserID` 取用户。
> 这是 F-020 真正的技术核心，不是加个界面那么简单。

## 3. 数据模型设计

### 3.1 DDL 变更（幂等 ALTER，见《05》§4）

```sql
-- admin_user 新增三列（均可空/常量默认，符合 SQLite ADD COLUMN 约束）
ALTER TABLE admin_user ADD COLUMN role TEXT NOT NULL DEFAULT 'admin';
ALTER TABLE admin_user ADD COLUMN force_password_change INTEGER NOT NULL DEFAULT 0;
ALTER TABLE admin_user ADD COLUMN updated_at TEXT;
```

| 列 | 类型 | 语义 |
|----|------|------|
| `role` | `TEXT NOT NULL DEFAULT 'admin'` | `owner` / `admin`；未知值一律按 `admin` 处理（fail-safe：降权而非提权） |
| `force_password_change` | `INTEGER NOT NULL DEFAULT 0` | `1` = 下次登录后必须改密才能调用管理 API |
| `updated_at` | `TEXT`（可空） | 最后变更时间，界面上展示 |

### 3.2 存量数据回填（幂等，由迁移 step v3 承担）

> **修订（对齐《06》§7）**：回填不再走 `main.go` 的 `EnsureOwnerBackfill` 调用，而是写进迁移 step `v3 admin_user_role` 的同一事务内。
> `EnsureAdmin` 在创建新 `admin` 时直接写 `role='owner'`（见 §4.7），因此新装库的 v3 step 天然空跑。

```sql
-- v3 step 内（与三列 ADD COLUMN 同一事务）：
UPDATE admin_user SET role = 'owner' WHERE username = 'admin' AND (role IS NULL OR role = '');
```

- 新装库：`EnsureAdmin` 创建时直接写 `role='owner'`，回填语句天然不影响（已是 owner）。
- 存量库：首次启动执行一次回填，之后条件不再命中 → 幂等。
- `force_password_change` 存量行全为 `0` → 无强制改密，符合预期。
- `updated_at` 存量为空 → 界面显示 `—`。

### 3.3 Go 模型（`model/model.go`）

```go
// 管理员角色常量（F-020：仅两级，细粒度权限列 P3）。
const (
	RoleOwner = "owner" // 超级管理员：可管理管理员账号
	RoleAdmin = "admin" // 管理员：项目/密钥/审计/改自己密码
)

type AdminUser struct {
	ID                  int64      `json:"id"`
	Username            string     `json:"username"`
	PasswordHash        string     `json:"-"`
	Role                string     `json:"role"`                 // 新增
	IsActive            bool       `json:"is_active"`
	ForcePasswordChange bool       `json:"force_password_change"` // 新增
	CreatedAt           time.Time  `json:"created_at"`
	UpdatedAt           *time.Time `json:"updated_at,omitempty"` // 新增
	LastLoginAt         *time.Time `json:"last_login_at,omitempty"`
	LastLoginIP         string     `json:"last_login_ip,omitempty"`
}
```

**角色归一化**（store 扫描时统一处理，杜绝库中脏值）：

```go
// normalizeRole 归一化角色：仅 owner 保留 owner，其余一律 admin（fail-safe 降权）。
func normalizeRole(s string) string {
	if s == RoleOwner { return RoleOwner }
	return RoleAdmin
}
```

### 4.2 P0 修正：`RequireAdmin` 按会话归属取用户

现状（`middleware.go:136`）：

```go
user, err := st.GetAdminByUsername(r.Context(), "admin")   // ❌ 硬编码
```

改为：

```go
// 按会话归属取当前管理员（F-020）：会话行已记录 admin_user_id，
// 不能再按固定用户名查（多账号下会把所有会话都解析成 admin）。
user, err := st.GetAdminByID(r.Context(), sess.AdminUserID)
if err != nil {
	if errors.Is(err, store.ErrNotFound) {
		fail(w, http.StatusUnauthorized, CodeSessionExpired, "会话缺失或过期")
		return
	}
	failService(w, err)
	return
}
if !user.IsActive {
	// 停用即刻失效：顺带吊销其全部会话（不仅拦当前请求）
	_ = st.DeleteSessionsByUser(r.Context(), user.ID)
	fail(w, http.StatusUnauthorized, CodeAccountDisabled, "账号已停用")
	return
}
if user.ForcePasswordChange && !forceChangeAllowed(r.URL.Path) {
	// 强制改密拦截：仅放行 白名单路径
	fail(w, http.StatusForbidden, CodeForbidden, "请先修改初始密码")
	return
}
```

**`forceChangeAllowed` 白名单**（仅这四条路径在强制改密期间可用）：

```go
// forceChangeAllowed 强制改密期间允许访问的路径白名单。
var forceChangeAllowedPaths = map[string]bool{
	"/api/v1/admin/me":      true,
	"/api/v1/admin/logout":  true,
	"/api/v1/admin/password": true,
	"/healthz":              true,
}
```

> 设计取舍：强制改密**必须后端拦截**。只在登录后让前端跳页的话，攻击者拿到会话 cookie 可直接打 API，改密就形同虚设。

### 4.3 P0 修正：`requireOwner` 中间件

```go
// requireOwner 要求当前会话用户角色为 owner（F-020：管理员账号管理仅 owner 可操作）。
// 挂在 RequireAdmin 之后：RequireAdmin(RequireOwner(handler))。
func requireOwner(next func(http.ResponseWriter, *http.Request)) func(http.ResponseWriter, *http.Request) {
	return func(w http.ResponseWriter, r *http.Request) {
		if u := currentUser(r); u == nil || normalizeRole(u.Role) != model.RoleOwner {
			fail(w, http.StatusForbidden, CodeForbidden, "仅超级管理员可执行此操作")
			return
		}
		next(w, r)
	}
}
```

装配方式（沿用现有 `requireAdmin` 包装风格）：

```go
requireAdmin := RequireAdmin(deps.Store)
requireOwner := func(h func(http.ResponseWriter, *http.Request)) func(http.ResponseWriter, *http.Request) {
	return requireAdmin(requireOwner(h))
}
```

### 4.4 角色与权限矩阵

| 能力 | owner | admin |
|------|:-----:|:-----:|
| 登录/登出/改自己密码 | ✅ | ✅ |
| 项目 CRUD、密钥生成/轮换/吊销 | ✅ | ✅ |
| 查看审计日志、仪表盘统计 | ✅ | ✅ |
| 系统设置（F-019 的保留策略等） | ✅ | ✅ |
| 管理员列表/新增/停用启用/改角色 | ✅ | ❌ 403/20104 |
| 重置他人密码 | ✅ | ❌ 403/20104 |
| 停用/降级**自己** | ❌ 409/20202 | ❌ 409/20202 |

### 4.5 关键业务规则（必须实现的四条护栏）

| 规则 | 实现 | 失败响应 |
|------|------|----------|
| **R1 至少一个启用 owner** | 任何会减少「启用 owner 数」的操作（停用 owner、降级 owner）前先 `CountActiveOwners()`，若该操作会使其归零则拒绝 | 409/20202「系统必须至少保留一个启用的超级管理员」 |
| **R2 不能操作自己** | 停用/降级/重置自己一律拒绝（避免自锁 + 语义混乱） | 409/20202「不能对自己执行此操作」 |
| **R3 停用即吊销会话** | `SetActive(false)` → `DeleteSessionsByUser(id)`，审计记 `sessions_revoked` | — |
| **R4 用户名规则** | `^[a-zA-Z0-9_.-]{3,32}$`，不得与既有冲突（UNIQUE → `store.ErrConflict` → 409/20201）；保留名 `admin` 可正常存在（初始账号） | 400/20003 或 409/20201 |

R1 的原子性：单连接下 `UPDATE` 与 `SELECT COUNT` 存在极小竞态窗口（本系统单实例单连接，实际请求串行，风险可接受）。若要严格，实现为单事务内「UPDATE ... WHERE id=? AND (SELECT count(*) FROM admin_user WHERE role='owner' AND is_active=1) > 1」。**推荐采用该写法**，成本极低。

### 4.6 密码与强制改密

- 新建管理员：`service.HashPassword`（argon2id）+ `validatePasswordStrength`（≥12 位含字母数字，**直接复用 `session_service.go` 现成函数**）。owner 在创建时输入初始密码（不走 `auth.log`/控制台通道——那只属于启动初始化的 D3 决策）。
- 重置他人密码：owner 输入新密码（同一强度校验），并置 `force_password_change=1`（默认行为，前端可勾选取消）。
- 用户自己改密成功后：`UpdateAdminPassword` 同时把 `force_password_change=0`（`session_service.go: ChangePassword` 需增这一步，**这是既有代码的必改点**）。
- 审计：创建/启停/改角色/重置密码各写一条（见《05》§2 的 6 个新事件）。

## 5. API 设计

### 5.1 `GET /api/v1/admins`（**需 owner**）

`?page=1&size=20`，沿用 `parsePagination`。

```jsonc
{ "code": 0, "data": {
  "total": 3, "page": 1, "size": 20,
  "items": [
    { "id": 1, "username": "admin", "role": "owner", "is_active": true,
      "force_password_change": false, "created_at": "2025-08-16T08:13:00Z",
      "updated_at": null, "last_login_at": "2026-01-01T10:00:00Z", "last_login_ip": "127.0.0.1" }
  ]
} }
```

**列表响应绝不包含 `password_hash`**（`json:"-"` 已在模型层兜底，双保险）。

### 5.2 `POST /api/v1/admins`（**需 owner**）

```jsonc
// 请求
{ "username": "alice", "password": "Str0ngPassw0rd!", "role": "admin" }
// 响应 201
{ "code": 0, "data": { "id": 2, "username": "alice", "role": "admin", "is_active": true } }
```

| 失败 | 响应 |
|------|------|
| 用户名已存在 | 409/20201 `name_conflict` |
| 用户名/密码不合法 | 400/20003 `validation_failed`（message 指明规则） |
| 非 owner 调用 | 403/20104 `forbidden` |

### 5.3 `PUT /api/v1/admins/{id}`（**需 owner**）

```jsonc
// 请求（部分更新，字段均可选）
{ "role": "owner", "is_active": false, "force_password_change": true }
```

| 场景 | 响应 |
|------|------|
| 正常改角色/启停 | 200 + 最新用户对象 |
| 目标是自己 | 409/20202「不能对自己执行此操作」 |
| 会导致无启用 owner | 409/20202「系统必须至少保留一个启用的超级管理员」 |
| 目标不存在 | 404/20200 |

### 5.4 `PUT /api/v1/admins/{id}/password`（**需 owner**）

```jsonc
{ "new_password": "N3wStrongPass!", "force_change": true }
```

成功 → 200 + `admin.password_reset` 审计；目标用户全部会话失效（`DeleteSessionsByUser`）。

## 9. 风险与回滚

| 风险 | 影响 | 缓解 |
|------|------|------|
| **中间件改动影响所有管理 API** | 若解析逻辑写错，全部管理接口 401 | 改动仅一行取数方式 + 新增 `TestRequireAdminUsesSessionOwner` 专项回归；先改 store 再改中间件，分两次提交 |
| 存量库缺 `role` 列 | 启动即崩 | 幂等 ALTER + 启动自检失败即退出（既有行为）；上线前必跑《05》§5 备份 |
| 唯一 owner 被误停 | 全员失去管理入口 | R1 + R2 双重护栏（service 校验 + 条件 UPDATE 原子保护）+ 前端按钮置灰 |
| 强制改密把用户锁死 | 无法访问任何管理 API | 白名单含 `password`/`me`/`logout`/`healthz`；且用户始终可用 owner 重置自救 |
| 角色脏值导致越权 | 严重 | `normalizeRole` fail-safe 降级：未知值一律 `admin`，只有精确 `owner` 才提权 |
| 回滚 | — | 备份 DB 三件套（《05》§5）；新列对旧二进制透明，旧版本仍能启动（但旧版本**不认角色**，等同全员 admin——回滚窗口内应避免新建账号） |
