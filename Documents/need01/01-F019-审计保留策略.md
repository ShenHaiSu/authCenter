# 01 F-019 审计保留策略 —— 施工设计

> need01 / 1 ｜ 里程碑 **M7** ｜ 依赖：无 ｜ 风险：低（无 schema 变更）
> 上游：需求 F-019「可配置审计日志保留天数，自动清理」

## 1. 目标与非目标

**目标**
1. 审计日志按可配置天数自动过期清理，磁盘占用可控。
2. 提供管理端入口：查看当前保留策略与用量、手动立即清理、可选手动回收空间。
3. 清理动作自身可审计（`system.audit_cleanup`），不破坏 D2「完整审计」决策。
4. 清理不拖慢认证主路径、不长时间独占数据库写锁。

**非目标（明确不做）**
- 不做审计表按月分表/分区（当前量级无需，YAGNI）。
- 不做自动 `VACUUM`（阻塞风险，见 §6）。
- 不做审计导出/归档包（列为 P3，见《README》§7 后续增强）。

## 2. 现状与缺口

| 项 | 现状 |
|----|------|
| settings 键 | `model.SettingAuditRetDays = "audit_retention_days"` **已定义但全仓库零引用**（唯一一处即定义处） |
| 清理任务 | 无 |
| 存储增长 | `audit_log` 只增；成功认证每次写 1 行，失败亦写 1 行（`auth_service.go`） |
| 索引 | `idx_audit_time(event_time)`、`idx_audit_type`、`idx_audit_actor` 已具备，删除按 `event_time` 走索引，代价可控 |
| 现有清理范式 | 只有会话惰性清理 `SessionStore.CleanupExpired`（登录时顺带），**审计不可照搬惰性**——没有访问就永不清理，正是要解决的问题 |

> 设计要点：审计清理必须**定时触发**（ticker），不能沿用会话的惰性范式；但要防「重启风暴」重复全表扫描（见 §4.2）。

## 3. 保留期语义（精确定义）

```
cutoff = now(UTC) - retention_days * 24h
删除集合 = { e ∈ audit_log | e.event_time < cutoff }   // 严格小于
```

| `retention_days` | 语义 |
|------------------|------|
| `0` | **永久保留**，任务不执行任何删除（仍会更新 `last_cleanup_at`，保持心跳语义一致） |
| `1..3650` | 正常保留；超出范围 → 400/20001 `invalid_parameter` |
| 未设置/非法字符串 | 回退默认 `90`，记 `warn` 日志（沿用 `loadRotateGraceDays` 容错风格） |

**保底行数 `audit_min_keep_rows`（默认 1000）**：即使 `retention_days=1`，若删除后总行数将低于该值，则**本次不删**（写 `system.audit_cleanup` success，`detail.reason="min_keep_guard"`）。
理由：避免误配置（如把 1 天当成 1 分钟）把唯一的审计证据清空。`min_keep_rows=0` 关闭保底。

判定实现（删除前查一次总数）：

```go
total, err := s.store.CountAudits(ctx)
if total > minKeep && total - int64(deletedSoFar) >= int64(minKeep) { 继续删 }
```

## 4. 后端设计

### 4.1 组件划分

```
store.AuditStore
  + DeleteAuditsBefore(ctx, cutoff string, limit int) (int64, error)   // 分批删除
  + CountAudits(ctx) (int64, error)                                    // 总行数
  + OldestAuditTime(ctx) (string, error)                               // 最早事件时间（界面展示）
  + CheckpointTruncate(ctx) error                                      // PRAGMA wal_checkpoint(TRUNCATE)

service.AuditRetentionService（新文件 internal/service/audit_retention_service.go）
  实现 service.Job 接口（框架见《06》§4，由 MaintenanceRunner 统一托管 ticker）：
  + Name() = "audit_cleanup"
  + Interval() = settings.audit_cleanup_interval_hours
  + Run(ctx) (Result, error)   // 幂等可重入；含心跳检查，RunNow 可跳过心跳
  + Config / UpdateConfig（校验 + 落 settings + 审计 settings.update）
  ⚠ 本 service **不再自己起 ticker / 不再自己管理锁**，互斥与生命周期由 MaintenanceRunner 负责

httpapi
  + handlers_settings.go（新）：GET/PUT /api/v1/settings、POST /api/v1/settings/audit/cleanup-now、
                              POST /api/v1/settings/audit/checkpoint
  + middleware RequireAdmin（已有，零改动）
```

**为何不放在 `AuditService`**：`AuditService`（44 行）职责是「写审计」，保留策略是运行期后台任务，生命周期独立（启动/停止/ticker），混在一起会让构造依赖变复杂。新建独立 service，与 `StatsService` 同级，符合现有 `service` 包按业务切分的惯例。

### 4.2 触发策略（定时 + 幂等心跳）

清理任务实现为 `service.Job`（接口定义见《06》§4），**ticker 与互斥由 `MaintenanceRunner` 统一托管**，本 service 只负责「跑一轮」的业务逻辑：

```go
// Name 任务名（日志/审计用）
func (s *AuditRetentionService) Name() string { return "audit_cleanup" }

// Interval 定时周期；读 settings.audit_cleanup_interval_hours，默认 24h
func (s *AuditRetentionService) Interval() time.Duration { return s.interval }

// Run 执行一轮清理。trigger 由 MaintenanceRunner 注入：
//   "timer"  → 定时触发，需先过心跳检查
//   "manual" → RunNow 手动触发，跳过心跳检查
// 互斥（TryLock）由 MaintenanceRunner 保证，本方法内不再重复加锁。
func (s *AuditRetentionService) Run(ctx context.Context) (service.Result, error) { ... }
```

规则：
1. **心跳幂等**：`now - last_cleanup_at < interval` 且 `trigger == "timer"` → 本轮跳过（返回 `Result{Affected:0, Detail:{"reason":"heartbeat_skip"}}`）。手动触发（`RunNow`）**跳过该检查**，强制执行。
2. **启动时对齐**：`main.go` 中 `maint.Start(ctx)` 之后不做立即清理；`MaintenanceRunner` 在注册 job 时读取 `Interval()` 并起对应计时器。由于心跳检查，**刚改完保留期重启不会立刻删数据**（除非距上次清理已超期），行为可预期。
3. **并发互斥**：`MaintenanceRunner` 对每个 job 独立 `TryLock`，手动与定时撞车时后者直接返回 `ErrJobRunning`（映射 409/20202）。
4. **失败不影响主流程**：任何错误只 `logger.Error` + 写 `failure` 审计，HTTP 服务照常。

### 4.3 分批删除（关键：不长时间占写锁）

单条 `DELETE FROM audit_log WHERE event_time < ?` 在百万行库上会独占单连接数秒，期间所有认证请求排队（单连接配置下这是硬约束）。
因此**分批 + 批间让出**：

```go
const (
	cleanupBatchSize = 1000              // 每批 1000 行
	cleanupBatchPause = 5 * time.Millisecond // 批间暂停，让单连接回到请求队列
	maxCleanupBatches = 1000             // 单轮上限 100 万行，防跑飞
)

func (s *AuditRetentionService) Run(ctx context.Context) (service.Result, error) {
	// 互斥已由 MaintenanceRunner 保证（见《06》§4），此处不再重复加锁。
	// trigger 由 runner 通过 context 值注入（"timer" / "manual"）。

	retention, err := s.loadConfig(ctx)
	if err != nil { return 0, err }
	now := timeNowUTC()

	if retention.Days == 0 && trigger != "manual" {   // 永久保留：只更新心跳
		return 0, s.markCleanup(ctx, now, 0, "retention_disabled")
	}

	cutoff := now.Add(-time.Duration(retention.Days) * 24 * time.Hour)
	var deleted, batches int64
	start := time.Now()

	for batches = 0; batches < maxCleanupBatches; batches++ {
		n, err := s.store.DeleteAuditsBefore(ctx, database.FormatTime(cutoff), cleanupBatchSize)
		if err != nil {
			s.writeCleanupAudit(ctx, "timer", cutoff, deleted, batches, time.Since(start), err)
			return deleted, err
		}
		deleted += n
		if n < cleanupBatchSize { break }   // 删完了
		select {
		case <-ctx.Done(): return deleted, ctx.Err()
		case <-time.After(cleanupBatchPause):
		}
	}
	// 保底行数保护（见 §3）
	...
	s.writeCleanupAudit(ctx, trigger, cutoff, deleted, batches, time.Since(start), nil)
	_ = s.store.CheckpointTruncate(ctx)   // 回收 WAL，见 §6
	return deleted, nil
}
```

store 层 SQL（**必须走子查询 LIMIT，避免一次锁全表**）：

```sql
DELETE FROM audit_log
 WHERE id IN (SELECT id FROM audit_log WHERE event_time < ? ORDER BY id LIMIT ?);
```

配合 `PRAGMA busy_timeout=5000`（已配置），批间暂停期间其他请求可正常获取连接。

### 4.4 空间回收策略（不自动 VACUUM）

SQLite 删除行只 freelist 化，文件不缩小。取舍：

| 手段 | 是否自动 | 理由 |
|------|---------|------|
| `PRAGMA wal_checkpoint(TRUNCATE)` | ✅ 清理后自动 | 轻量、毫秒级、把 `-wal` 截断为主库文件，**大部分空间能还回文件系统** |
| `PRAGMA incremental_vacuum` | ❌ 不自动 | 需开启 `auto_vacuum=INCREMENTAL`（只能在空库建库时设定，存量库改不了），不通用 |
| `VACUUM` | ❌ 仅手动 | 会重写整库、持有排他锁，运行时长与库大小成正比，**绝不能自动执行** |

手动 VACUUM 的替代方案：提供 `POST /api/v1/settings/audit/checkpoint`（即 TRUNCATE checkpoint），并在前端以文案说明「如需真正缩小 db 文件，请在停机后执行 `sqlite3 data/authcenter.db 'VACUUM;'`」。
这是**有意为之的克制**：不为省几 MB 引入运行时长阻塞风险。

### 4.5 启动装配（`cmd/authcenter/main.go`）

清理任务注册到 `MaintenanceRunner`，由它统一托管生命周期（放在 `signal.NotifyContext` 之后，保证能随 SIGINT 退出）：

```go
// M7：审计保留策略后台任务（settings.audit_retention_days，默认 90 天，0=永久保留）
retentionSvc := service.NewAuditRetentionService(st, auditSvc, logger)  // 实现 service.Job
settingsSvc := service.NewSettingsService(st, auditSvc, logger)
...
maint := service.NewMaintenanceRunner(st, auditSvc, logger)
maint.Register(retentionSvc)
maint.Start(ctx)   // ctx 来自 signal.NotifyContext，随优雅关闭自动停止
```

> 前提：M7 开工前已按《06》§4 落地 `MaintenanceRunner`（作为「步骤 2」的基础设施提交）。
> 若 `MaintenanceRunner` 尚未就绪，可临时保留本 service 自管 ticker 的实现，但**必须在 M7 结束前切换过来**，避免两套机制并存。

`RouterDeps` 增加 `Settings *service.SettingsService`、`Retention *service.AuditRetentionService` 两个字段（沿用现有 `deps.Stats != nil` 的可选装配风格）。

## 5. API 设计（全部需 `RequireAdmin`）

### 5.1 `GET /api/v1/settings`

返回白名单（**绝不返回 `jwt_secret`**，沿用 06 §3.4）：

```jsonc
{ "code": 0, "message": "ok", "data": {
  "settings": {
    "audit_retention_days": 90,
    "audit_cleanup_interval_hours": 24,
    "audit_min_keep_rows": 1000,
    "audit_last_cleanup_at": "2026-01-01T00:00:00Z",   // 空表示从未清理
    "audit_last_cleanup_rows": 0
  },
  "usage": { "total_rows": 12345, "oldest_event_time": "2025-10-02T08:00:00Z" }
} }
```

### 5.2 `PUT /api/v1/settings`

```jsonc
// 请求（部分更新，未出现的键保持不变）
{ "audit_retention_days": 180, "audit_cleanup_interval_hours": 12, "audit_min_keep_rows": 5000 }
```

响应 `{ "settings": { ...更新后的白名单... } }`。
校验失败 → 400/20001 + `message` 指明字段与范围（例：`audit_retention_days 必须在 0..3650`）。
写 `settings.update` 审计（见《05》§2）。
**边界保护**：`retention_days` 变小会立即导致下一轮清理删除数据 → 前端必须二次确认（见 §7），后端不额外阻断。

### 5.3 `POST /api/v1/settings/audit/cleanup-now`

手动立即执行一轮（跳过心跳检查，保留保底行数与分批规则）。

```jsonc
{ "code": 0, "data": { "deleted_rows": 3200, "duration_ms": 41, "cutoff": "2025-10-03T00:00:00Z" } }
```

| 情况 | 响应 |
|------|------|
| `retention_days=0` | 200，`deleted_rows: 0`，`message` 注明「当前设置为永久保留，未执行删除」 |
| 已有清理在跑 | 409/20202 `state_conflict`（`ErrJobRunning`，由 `MaintenanceRunner` 返回，见《06》§4） |
| 库内失败 | 500/50000，**已删除的部分不回滚**（分批语义），审计记录已删行数 |

### 5.4 `POST /api/v1/settings/audit/checkpoint`

执行 `PRAGMA wal_checkpoint(TRUNCATE)`，返回 `{"truncated": true, "wal_bytes": 0}`。用于「已清理但 db 文件没变小」时的即时缓解。

## 7. 审计与安全

| 项 | 设计 |
|----|------|
| 清理自身审计 | `system.audit_cleanup`，`detail` 含 `deleted_rows`/`cutoff`/`duration_ms`/`batch_count`/`trigger`（`timer`/`manual`）/`reason`（`min_keep_guard`/`retention_disabled`） |
| 配置变更审计 | `settings.update`，只记键名与值哈希，不记原值（防未来把敏感项写进审计） |
| 不可逆提示 | 前端必须显式提示「删除不可恢复」；API 文档标注为破坏性操作 |
| 越权 | 全部端点走 `RequireAdmin`（当前系统单角色，暂不区分 owner——owner 细分在《02》落地后由 `RequireOwner` 覆盖，见《04》§4 说明） |

### 8.3 手工验收（对齐 08 §4 风格）

1. 开发模式启动，设 `audit_retention_days=1`，造两天前的审计（可直接改库 `UPDATE audit_log SET event_time=...`）。
2. 点「立即清理」→ toast 提示删除行数；`GET /audit-logs?from=两天前` 返回 0 条，近期记录完好。
3. 重启 → 控制台无异常；`system.audit_cleanup` 只在清理时新增，不在每次启动新增。
4. 设 `retention_days=0` → 再点清理 → 提示「永久保留，未执行删除」。
5. 停服 → 查 `data/authcenter.db` 大小应小于清理前（WAL 已 truncate）。
