        ↓

        ↓

**依赖关系**
- 步骤 2 → 全部：`migrate.go` 与 `maintenance.go` 是三份设计的共用底座，**必须先合入**；但步骤 2 自身无 DDL 变更（只做框架 + v1 基线包装），可独立评审合入。
- F-019 → F-021：F-021 的加密状态展示**放在 F-019 建的 `settings` 视图里**，故 F-019 先行。
- F-020 与 F-021：无代码依赖，但**共用 step 注册表**（v2 / v3 按顺序登记）。
- 三者互不阻塞：若要并行，先把步骤 2 单独提交并合入，再分支开发。

## 4. 里程碑出口（Definition of Done）

每个里程碑必须同时满足：

1. **代码**：本设计各文档「实施步骤」全部完成，无 TODO 残留。
2. **门禁**：`CGO_ENABLED=0 go build ./...`、`go vet`、`gofmt -l` 无输出、`go test ./...` 全绿。
3. **测试**：本文档 §3 回归矩阵全绿 + 本里程碑专属用例（各设计文档的测试清单章节）全绿。
4. **性能**：基准已跑，数值记录进验收报告，与 M6 基线对比无超预算项。
5. **产物**：`build.ps1`/`build.sh` 成功，`Bundle/{windows,linux}` 产物更新 + `SHA256SUMS.txt` 刷新。
6. **文档**：见 §6 回写清单。
7. **验收报告**：在 `Documents/backEndArchitect/` 下新增 `14-M7…`、`15-M8…`、`16-M9…` 报告（体例对齐现有 `09~13`：范围 → 逐项核验表 → 基准数据 → 交付文档 → 验收矩阵 → 结论）。
8. **提交拆分**：按「后端 / 前端 / 测试 / 文档」分批提交，不把三项功能混在一次提交里（沿用仓库既有 commit 风格：`feat(scope):` / `fix:` / `docs:` / `build:`）。

每个提交都必须能独立 `go build` 通过（第 2/3 步允许测试未补齐，但不允许编译失败）。
