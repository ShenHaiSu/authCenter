# 03 F-021 密钥存储加密 —— 施工设计

> need01 / 3 ｜ 里程碑 **M8** ｜ 依赖：`internal/database/migrate.go`（《05》§4 幂等 ALTER 规范）｜ 风险：中高（认证主路径 + 数据迁移）
> 上游：需求 F-021「可选 AES-GCM 加密密钥列（密钥来自环境变量），缓解明文落盘风险」

## 1. 目标与非目标

**目标**
1. `api_key.key_value` 在启用后以 **AES-256-GCM** 密文落盘，DB 文件泄露不再等于密钥泄露。
2. 主密钥**只来自环境变量**，不入库、不落盘、不进日志、不进审计。
3. 认证主路径（`GetKeyByValue`）改造为**按 SHA-256 哈希等值查询**，不因密文而退化为全表扫描。
4. 启动自检：主密钥可用则必须能解开库中密文，解不开 → **退出并报错**（fail-fast，绝不带病启动）。
5. 支持存量密钥**原地回填**加密；加密为**单向棘轮**（只提供启用，不提供运行时降级为明文，理由见 §4.6）。
6. 前后端行为、对外认证业务码语义**完全不变**。

**非目标（明确不做）**
- 不做密钥分片/信封加密（KMS/HSM）——单二进制内网部署，无 KMS 依赖。
- 不做主密钥轮换的在线重加密流程（版本字段已预留 `key_encryption_version`，轮换列 P3）。
- 不加密 `admin_user.password_hash`（argon2id 已是单向哈希，无需加密）。
- 不改变密钥明文的对外形态（客户端仍用原 40 位明文调用认证）。

## 2. 威胁模型与取舍

| 攻击面 | 加密前 | 加密后 |
|--------|--------|--------|
| DB 文件被拷走/误传/备份泄露 | **全部密钥即刻失守**（明文列） | 仅得密文；无主密钥无法还原（`data/` 目录 0700 + 文件 0600 已是第一道防线，加密是第二道） |
| 运维误执行 SQL / 第三方工具导出 | 明文外泄 | 密文外泄 |
| 内存/日志/审计泄露 | 已有防护（`json:"-"`、脱敏红线、审计禁写明文） | 不变 |

**明确不防的**：已获得主密钥的攻击者（等价于完全控制进程）、SQL 注入直接读 `settings`（主密钥不在库里，所以此路不通）、以及「攻击者能改库」的场景——此时他可把 `key_hash` 指向自己的 `key_value`。
对最后一条的部分缓解：解密时用 **AAD 绑定明文密钥**（§4.3），密文与哈希不自洽的组合会在解密时报错并落到「认证失败 + 审计」，不会静默放行。

**哈希选型说明**：`key_hash = SHA-256(明文密钥)`。这里**故意不用 argon2/bcrypt**——密钥是 40 位 `A-Za-z0-9` 随机串（熵 ≈238 bit，文档 06 §2），无需抗 GPU 暴力破解；用慢哈希只会把认证主路径拖慢三个数量级。

## 3. 数据模型设计

### 3.1 DDL 变更（幂等 ALTER + 索引，见《05》§4）

```sql
ALTER TABLE api_key ADD COLUMN key_hash TEXT;            -- 可空：存量行启动时回填
ALTER TABLE api_key ADD COLUMN key_value_enc INTEGER NOT NULL DEFAULT 0;  -- 0=明文 1=AES-GCM
CREATE UNIQUE INDEX IF NOT EXISTS idx_key_hash ON api_key(key_hash);      -- 部分唯一
```

| 列 | 语义 |
|----|------|
| `key_hash` | `hex(SHA-256(明文密钥))`；两种模式下都写入，认证查询统一走该索引（模式切换无需重建索引） |
| `key_value_enc` | `0`=明文模式（`key_value` 存明文）；`1`=密文模式（`key_value` 存 `base64(nonce‖ct‖tag)`）。**同一列承载两种形态，由本标志位判定**（方案 A，见下） |

**密文存放列的取舍**（重要设计决策）：

| 方案 | 做法 | 评价 |
|------|------|------|
| A（**采纳**） | 复用 `key_value` 列存 `base64(nonce‖ciphertext‖tag)`，用 `key_value_enc` 区分模式 | 零新增大列、无需改所有读取 SQL 的列名，改动面最小 |
| B | 新增 `key_value_cipher` 列，两列并存 | 列多一倍，NULL 语义混乱，收益仅是「模式一眼可见」，不值得 |

采用方案 A：`key_value` 存「明文或密文」，由 `key_value_enc` 判定。**所有读取路径必须先看该标志位**，这是本设计最容易出错的地方（§4.4 给出统一解包函数强制收口）。

`key_hash` 的唯一性：明文与密文模式下**都**必须写入 hash（认证查询统一走 hash 索引，模式切换时无需重建索引）。

### 3.2 存量回填（分批，**后台任务，不阻塞启动**）

> **修订（对齐《06》§4）**：`key_hash` 回填**不在启动路径上执行**。启动只做 DDL（迁移 step v2）与状态自检；回填由 `MaintenanceRunner` 托管的后台 job 异步完成，重启速度与密钥条数无关。

```sql
-- 后台 job 内的分批回填：每批 1000 行，按 id 升序（与 F-019 分批思路一致，避免长事务）
SELECT id, key_value FROM api_key
 WHERE key_hash IS NULL AND key_value <> '' ORDER BY id LIMIT 1000;
-- 应用层算 SHA-256 后：
UPDATE api_key SET key_hash = ? WHERE id = ?;
```

- 幂等：条件 `key_hash IS NULL` 不再命中即结束 → 重复运行安全。
- 回填**不需要主密钥**（hash 与加密无关）。
- 状态写 settings：`key_hash_backfill_state` = `pending` → `running` → `done`，完成时写 `key_hash_backfill_done_at` 与审计 `system.key_encryption_migrated`（`mode=backfill_hash`）。
- **回填未完成期间（`pending`/`running`）认证走兼容路径**：先按 `key_hash` 查；查不到时回落到旧的 `key_value` 明文等值查询（仅当该行 `key_value_enc=0`）。回填完成后自动切回纯 hash 路径（详见 §4.4 兼容分支）。
- 若某批触发 UNIQUE 冲突（理论上的 hash 碰撞）：该批回滚、job 停止、写 `failure` 审计并告警，**不静默跳过**。

### 4.2 主密钥来源与解析

环境变量：**`AUTHCENTER_KEY_ENC_KEY`**（与既有 `AUTHCENTER_JWT_SECRET` 同一模式，写入 `config.Config.KeyEncKey`）。

```go
// ParseMasterKey 解析主密钥：base64(标准编码) 解码后必须恰好 32 字节。
// 空字符串 → 返回 nil（调用方装配 PlainCipher，即未启用加密）。
// 长度不符 → 报错，启动失败（fail-fast，绝不静默降级为明文模式）。
func ParseMasterKey(b64 string) ([]byte, error) {
	if b64 == "" { return nil, nil }
	raw, err := base64.StdEncoding.DecodeString(b64)
	if err != nil {
		return nil, fmt.Errorf("AUTHCENTER_KEY_ENC_KEY 不是合法 base64: %w", err)
	}
	if len(raw) != 32 {
		return nil, fmt.Errorf("AUTHCENTER_KEY_ENC_KEY 解码后为 %d 字节，要求 32 字节", len(raw))
	}
	return raw, nil
}
```

生成命令（写进 README / Bundle README / systemd `EnvironmentFile` 说明）：

```bash
# Linux/macOS
export AUTHCENTER_KEY_ENC_KEY=$(head -c 32 /dev/urandom | base64)
# Windows PowerShell
$env:AUTHCENTER_KEY_ENC_KEY = [Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))
```

**fail-fast 规则（红线）**：
- 设了 `key_encryption_enabled=1` 但**没设** env → 启动失败，报错「已启用密钥加密但未提供 AUTHCENTER_KEY_ENC_KEY」。
- 设了 env 但库中无密文 → 允许启动（预配置模式），日志提示「主密钥已加载，当前库中暂无密文密钥」。
- 启动时用主密钥试解一条密文（最多试 1 条）→ 失败则写 `system.key_encryption_verify_failed` 审计 + 返回错误退出。**主密钥绝不进日志/审计/错误信息**。

### 4.3 加解密实现

```go
const cipherVersion = "aes-256-gcm-v1"
const aadPrefix = "authcenter:api_key:v1"   // AAD 前缀，版本演进时可区分

// Seal 加密：nonce(12B, crypto/rand) ‖ ciphertext ‖ tag(16B) → base64(StdEncoding)。
func (c *GCMCipher) Seal(plain string) (string, error) {
	nonce := make([]byte, 12)
	if _, err := rand.Read(nonce); err != nil {
		return "", fmt.Errorf("生成 nonce 失败: %w", err)
	}
	// AAD 绑定版本前缀 + 明文密钥本身：
	//   · 版本前缀 → 未来换算法时旧密文不会被误当新格式解开
	//   · 明文密钥 → 密文与 key_hash 必须自洽，防止「改库指路」类攻击
	sealed := c.aead.Seal(nonce, nonce, []byte(plain), []byte(aadPrefix+plain))
	return base64.StdEncoding.EncodeToString(sealed), nil
}

func (c *GCMCipher) Open(stored string) (string, error) {
	raw, err := base64.StdEncoding.DecodeString(stored)
	if err != nil || len(raw) < 12+16 {
		return "", ErrCipherMalformed
	}
	nonce, body := raw[:12], raw[12:]
	// AAD 需要明文密钥，而它正是待解的内容 → 先用「候选明文」无法构造 AAD。
	// 解法：Open 接收调用方传入的候选明文（认证路径天然有；管理路径由调用方给出行内明文）。
	plain, err := c.aead.Open(nil, nonce, body, []byte(aadPrefix+candidate))
	if err != nil {
		return "", ErrCipherDecrypt
	}
	return string(plain), nil
}
```

> **AAD 的实现取舍（重要且刻意）**：GCM 的 AAD 在加密时必须已知，而解密前明文未知。
> 本设计让 `Open(stored, candidate string)` 接收**调用方手里的候选明文**：
> - 认证路径：候选明文 = 客户端提交的 `key`（天然存在）→ 解不开即认证失败，语义完美。
> - 管理路径（列表/详情展示）：候选明文 = 该行 `key_value`（明文模式）或解密结果本身——**明文模式不需要解密**；密文模式下列表**永不展示明文**（沿用现状：`json:"-"` + 前端只显示指纹/备注），因此管理路径**根本不需要解密**。
>
> 结论：**只有认证路径需要 Open**，且总是带着候选明文。这让 AAD 绑定既可行又零额外成本。

**恒定时间比对**：解密成功后，仍用 `subtle.ConstantTimeCompare` 比对明文与候选（纵深防御，正常情况下二者必相等）。

### 4.4 统一解包（强制收口，避免模式判断散落）

```go
// ResolvePlain 统一还原某条密钥记录对应的明文，并校验与 key_hash 自洽。
//   mode 0：key_value 即明文，直接返回
//   mode 1：用候选明文 candidate 走 GCM 解密；解密后必须与 key_hash 匹配
// 调用约定：**只有认证路径调用**（其他路径按现状永不返回明文）。
func ResolvePlain(k *model.APIKey, c Cipher, candidate string) (string, error) {
	if k.KeyValueEnc == 0 {
		return k.KeyValue, nil
	}
	plain, err := c.Open(k.KeyValue, candidate)
	if err != nil {
		return "", ErrCipherDecrypt
	}
	if HashKey(plain) != k.KeyHash || subtle.ConstantTimeCompare([]byte(plain), []byte(candidate)) != 1 {
		return "", ErrCipherDecrypt   // 密文与哈希不自洽 → 视为无效
	}
	return plain, nil
}
```

`ApiKeyService.KeyForAuth` 是唯一对外入口：

```go
// KeyForAuth 认证取密钥：先按 hash 索引定位记录，再用提交密钥完成解密/明文比对。
// 语义与旧 GetKeyByValue 完全一致：不存在 → store.ErrNotFound。
//
// 兼容分支（仅当 settings.key_hash_backfill_state != "done" 时启用，见《06》§4）：
// 回填未完成期间，仍可能有存量行的 key_hash 为 NULL。此时回落一次明文等值查询，
// 命中后顺手把该行 key_hash 补上（自愈式回填，摊平后台 job 的工作量）。
// 该分支在回填完成后自动失效（状态为 done），不引入长期性能负担。
func (s *ApiKeyService) KeyForAuth(ctx context.Context, plainKey string) (*model.APIKey, error) {
	k, err := s.store.GetKeyByHash(ctx, HashKey(plainKey))
	if err != nil && errors.Is(err, store.ErrNotFound) && s.backfillPending() {
		if k, err = s.store.GetKeyByValuePlain(ctx, plainKey); err == nil {
			go s.tryFillHashAsync(ctx, k.ID, plainKey) // 异步补 hash，不阻塞认证响应
		}
	}
	if err != nil {
		return nil, err   // ErrNotFound → auth_service 记 key_not_found，对外 10004，语义不变
	}
	if _, err := ResolvePlain(k, s.cipher, plainKey); err != nil {
		// 记录异常：密文/哈希不自洽或密钥不匹配 → 内部原因，对外仍按 key_not_found
		s.logger.Error("密钥解密失败", "key_id", k.ID, "err", err)
		s.audit.Log(ctx, &model.AuditLog{ /* auth.authenticate_failed, detail.reason="decrypt_failed" */ })
		return nil, store.ErrNotFound
	}
	return k, nil
}
```

> `backfillPending()` 读 `settings.key_hash_backfill_state`（进程内缓存，**变更时由 settings 写路径失效**，避免每次认证都查库）。
> `tryFillHashAsync` 用 `context.WithoutCancel(ctx)` + 独立超时，避免请求 ctx 取消导致补写丢失；失败仅记日志。

`auth_service.go` 第 5 步改为：

```go
key, err := s.apikeys.KeyForAuth(ctx, req.Key)   // 原：s.store.GetKeyByValue(ctx, req.Key)
```

> **保持对外语义不变**（红线）：解密失败一律归一为「密钥不存在」→ 业务码 `10004 key_not_found`，不新增对外码值（见《05》§3）。

### 4.5 写入路径改造

| 路径 | 改造 |
|------|------|
| `ApiKeyService.Create` | 生成 40 位明文 → `hash := HashKey(plain)`；若 `cipher.Enabled()` 则 `stored, _ = cipher.Seal(plain)`、`key_value_enc=1`；返回给前端的**仍是明文 `plain`**（一次性展示逻辑不变） |
| `ApiKeyService.Rotate` | 同上；旧密钥只改 `expires_at`（`UpdateKey` 不动 `key_value`/`key_hash`） |
| `ApiKeyService.Update` | 走 `UpdateKey`（只改 name/expires/fingerprint/is_active），**不触碰加密列** |
| 迁移回填（F-019 分批范式） | 见 §3.2 |

**易错点提醒**：`store.CreateKey` 的 INSERT 语句必须同时写 `key_hash` 与 `key_value_enc`，漏写会导致认证查不到密钥（表现为全部 `key_not_found`）——必须由集成测试 `TestKeyLifecycle` 全链路覆盖。

### 4.6 启停加密（管理端）

| 操作 | 前置条件 | 过程 | 结果 |
|------|---------|------|------|
| **启用** | env 已提供主密钥；`key_hash` 回填已完成 | 逐行 `Seal(明文)` → 事务内 `UPDATE key_value=密文, key_value_enc=1`（**按批提交**，每批 1000 行） | `key_encryption_enabled=1`、`key_encryption_version=aes-256-gcm-v1`、写 `system.key_encryption_migrated` |
| **关闭** | env 仍提供主密钥；库中**存在密文** | 逐行 `Open(密文, 候选=?)`… 见下 | 见「回退实现说明」 |
| 启停后 | — | 立即生效（新写入走新模式）；**已存在的客户端密钥不变**（明文对客户端透明） | — |

**回退实现说明（诚实的设计取舍）**：关闭加密需要把密文还原成明文，而还原需要明文本身（正是 AAD 绑定的代价）。
解法：`Open` 的 AAD 已绑定明文，因此**必须先有明文才能解密**——这在「只有密文」的库里是一个死锁。

三种可选实现（**推荐第 1 种**）：

1. **不做「关闭加密」功能**（推荐）：只提供「启用」。关闭加密的操作方式是「用正确主密钥启动 + 执行一次性离线工具 `cmd/keydecipher` 导出明文副本 → 用该副本重建库」。理由：加密一旦开启就该是单向棘轮，运行时提供「一键降级为明文」是**降低安全性**的 API，不该存在。
2. 提供 `POST /disable`：在 `cmd` 侧实现「逐行用 `key_hash` 无法还原」→ 不可行，否决。
3. 保留 `key_value` 明文列 + 另加密列（方案 B）：可双向，但放弃本设计的核心收益（明文仍在库里）。

**结论**：本设计**只提供启用，不提供运行时关闭**。`settings.key_encryption_enabled` 不可通过 API 置 0；如需彻底回到明文，走离线重建流程并在文档中给出命令。这样 API 面更小、更安全。

### 4.7 启动装配（`cmd/authcenter/main.go`）

在既有 `ensureJWTSecret` 之后、service 装配之前插入：

```go
// M8：密钥存储加密（主密钥只来自 env AUTHCENTER_KEY_ENC_KEY，缺失即明文模式）
keyCipher, err := service.NewCipherFromEnv(cfg.KeyEncKey)   // 长度非法 → 启动失败
if err != nil {
	return err
}
if err := ensureKeyEncryptionReady(auditCtx, st, keyCipher, logger); err != nil { // **仅状态自检，不做数据回填**
	return err
}
...
apikeySvc := service.NewApiKeyService(st, auditSvc, projectSvc, graceDays, keyCipher)
authSvc := service.NewAuthService(auditCtx, st, auditSvc, tokenSvc, logger, apikeySvc)  // 签名新增 apikeys（用于 KeyForAuth）
```

装配完成后（`signal.NotifyContext` 之后）注册后台回填任务：

```go
maint := service.NewMaintenanceRunner(st, auditSvc, logger)   // 《06》§4，M7 已引入
backfillSvc := service.NewKeyHashBackfillService(st, auditSvc, logger)
maint.Register(backfillSvc)
maint.Start(ctx)
go maint.RunNow(ctx, "key_hash_backfill")   // 异步触发一次；不阻塞 HTTP 启动
```

`ensureKeyEncryptionReady` 职责（全部幂等，**不含数据回填**）：
1. 读 `key_encryption_enabled`：为 `1` 而 `keyCipher` 为 `PlainCipher` → **报错退出**。
2. 模式一致性检查：存在 `key_value_enc=1` 的行但无主密钥 → 报错退出。
3. 有密文时试解 1 条验证主密钥正确；失败 → 写 `system.key_encryption_verify_failed` + 报错退出。
4. 初始化 `key_hash_backfill_state`（缺失则写 `pending`；已完成过则保持 `done`）。
5. 全部通过 → 记 `Info` 日志（只说「N 条密文密钥，主密钥校验通过」，**不打任何密钥内容**）。

> **schema 版本保护**（见《06》§3.3）：库 `user_version` 高于本二进制支持的版本时，`database.Open` 已先行拒绝启动，
> 因此「旧二进制读加密库」这一最危险场景被拦截在启动期，而不是运行期认证全断。

### 4.8 配置项

| 项 | 值 | 说明 |
|----|----|------|
| `AUTHCENTER_KEY_ENC_KEY` | base64(32B) | **新增 env**；`config.EnvKeyEncKey` 常量 + `Config.KeyEncKey` 字段（仿 `EnvJWTSecret`） |
| `-key-encryption` flag | **不提供** | 主密钥属秘密，只能走 env（与 JWT secret 一致） |
| `settings.key_encryption_enabled` | `1`/`0` | 记录加密是否已启用（启用动作写入，**不可通过 API 置 0**） |
| `settings.key_encryption_version` | `aes-256-gcm-v1` | 为未来轮换预留 |
| `settings.key_encrypted_count` | int | 密文密钥条数（界面展示/自检） |

### 5.2 `POST /api/v1/settings/key-encryption/enable`（需会话；破坏性）

```jsonc
{ "code": 0, "data": { "encrypted_rows": 12, "duration_ms": 8, "mode": "encrypted" } }
```

| 情况 | 响应 |
|------|------|
| env 未提供主密钥 | 409/20202「未配置 AUTHCENTER_KEY_ENC_KEY，无法启用加密」 |
| 已是加密模式 | 409/20202「密钥存储已处于加密模式」 |
| 回填过程失败 | 500/50000（**已提交批次不回滚**，可重跑：未加密行会被再次处理） |
| 成功 | 200 + 写 `system.key_encryption_migrated` |

**注意**：启用动作只改存储形态，**对外认证行为零变化**（明文对客户端透明），因此不需要通知任何接入方。

## 9. 风险与回滚

| 风险 | 影响 | 缓解 |
|------|------|------|
| **主密钥丢失** | 全部密钥不可恢复，认证全断 | 文档强调「先备好主密钥再启用」；启用接口需二次确认；建议把主密钥存进密码管理器而非仅 env |
| env 漏配导致带病启动 | 加密形同虚设且不易察觉 | `key_encryption_enabled=1` 而无主密钥 → **启动失败**（不降级） |
| 密文/哈希不自洽导致全量认证失败 | 服务不可用 | 上线前必跑《05》§5 备份；`TestStartupFailsWithWrongMasterKey` 覆盖；提供离线自检命令（见下） |
| 模式判断散落导致漏解密 | 部分路径返回密文当明文 | 统一收口到 `ResolvePlain`，且只有认证路径调用；集成测试覆盖创建/轮换/认证/启停四条主路径 |
| INSERT 漏写 `key_hash` | 认证全失败 | `TestKeyCreatedEncryptedWhenEnabled` + 全量 `TestKeyLifecycle` 回归 |
| 性能回退 | 认证 P99 超预算 | 补 3 个基准；SHA-256 + AES-GCM 均为 µs 级，预算内；超预算则评估异步审计（预留策略） |
| **回滚** | 密文库被旧二进制读取 → 认证全失败 | 旧二进制**不认识** `key_value_enc`，会把 base64 密文当明文比对 → 认证必然失败。故回滚必须用**启用前的备份**（《05》§5），不能只换二进制。**这是本设计唯一不可逆的操作，文档必须显著标注。** |
