# 06 数据库迁移与版本追踪 —— 施工设计

> need01 / 6 ｜ 前置基础设施（建议在 M7 开工前的「步骤 2」单独落地）｜ 依赖：无
> 解决两个问题：①当前**没有 schema 版本追踪**（`migrations []string` 顺序执行，无法查询库处于第几版、无法做条件迁移）；
> ②F-021 的 `key_hash` 回填若放在启动路径上，大表会拖慢重启。

## 1. 现状与缺口（已核实）

| 项 | 现状 |
|----|------|
| 迁移入口 | `database.Open()` → `migrate(db)`，`main.go:58` 启动时调用 |
| 迁移内容 | `var migrations = []string{...}`，6 段 `CREATE TABLE IF NOT EXISTS` |
| 幂等性 | 靠 `IF NOT EXISTS`，**靠 DDL 自身幂等**，而非靠版本判断 |
| 版本记录 | **无**。既没有 `schema_version` 表，也**没有使用 SQLite 内置的 `PRAGMA user_version`**（已 grep 确认） |
| 降级保护 | **无**。旧二进制拿到新库会直接运行（对 F-021 加密库而言 = 认证全断） |
| 回填 | 无任何数据回填先例 |

**为什么现在补**：F-020 与 F-021 各要加列 + 做数据回填，且 F-021 引入「旧二进制不可用」这一不可逆边界。没有版本号就无法在启动时拦住危险降级。

## 2. 版本模型

| 决策 | 结论 | 理由 |
|------|------|------|
| 权威来源 | **`PRAGMA user_version`**（SQLite 内置，32 位整数，随事务原子提交） | 免建表、免维护、与 DDL 同事务，不会出现"表里记着 v3、实际 DDL 没执行"的分裂 |
| 是否再存 `settings.schema_version` | **不存** | 双源必然发散；确有展示需求时从 `user_version` 读出并放进 API 响应即可 |
| 版本语义 | 整数单调递增，每个**不可分割的变更**占一个版本号 | 便于排障（"库在 v3"）与精确回填 |
| 幂等责任 | **由每个 step 内部保证**（`ensureColumn` / 条件 UPDATE） | 版本号只用于「该不该跑」，不用于「能不能重复跑」；两者解耦后，即使版本号意外写错也不会破坏数据 |
| 新库基线 | 现有 6 表建齐后写入 `user_version = 1` | 存量库首次启动时也补写为 1（此时 6 表已存在，幂等） |

**`user_version` 取值/写入**：

```go
func schemaVersion(db *sql.DB) (int, error) {
	var v int
	if err := db.QueryRow("PRAGMA user_version").Scan(&v); err != nil {
		return 0, fmt.Errorf("读取 schema 版本失败: %w", err)
	}
	return v, nil
}

func setSchemaVersion(db *sql.DB, v int) error {
	if _, err := db.Exec(fmt.Sprintf("PRAGMA user_version = %d", v)); err != nil {
		return fmt.Errorf("写入 schema 版本 %d 失败: %w", v, err)
	}
	return nil
}
```

> `PRAGMA user_version = N` **不能**用占位符传参，必须格式化拼接；`N` 来自代码内常量表（非用户输入），无注入面。实现时加一行注释说明这一点，避免后人改成拼接外部输入。

## 3. 迁移框架（`internal/database/migrate.go`）

### 3.1 step 注册表

```go
// step 单个迁移步骤：版本号单调递增，Name 仅用于日志/审计。
// Up 内部必须自身幂等（ensureColumn / 条件 UPDATE），版本号只决定「该不该执行」。
type step struct {
	Version int
	Name    string
	Up      func(*sql.DB) error
}

// migrationSteps 迁移步骤表。**只允许在末尾追加，禁止修改历史步骤。**
// 约定：DDL 与其数据回填写在同一个 step 的同一事务内，保证「结构与数据」要么都成功要么都不做。
// **版本号按落地顺序分配**（先合入者先得），与设计文档编号无关；
// 当前里程碑顺序为 M8 先于 M9，因此 F-021 占 v2、F-020 占 v3。
var migrationSteps = []step{
	{Version: 1, Name: "baseline_tables", Up: upBaselineTables},        // 现有 6 张表（从 migrations 迁入）
	{Version: 2, Name: "api_key_hash", Up: upApiKeyHashColumns},        // F-021（M8）：两列 + 索引（回填见后台 job）
	{Version: 3, Name: "admin_user_role", Up: upAdminUserRole},          // F-020（M9）：三列 + owner 回填
	// 未来：{Version: 4, Name: "...", Up: ...}
}

// targetSchemaVersion 当前二进制期望的 schema 版本（= 最高注册版本）。
func targetSchemaVersion() int { return migrationSteps[len(migrationSteps)-1].Version }
```

### 3.2 执行流程

```go
// applyMigrations 迁移主流程：
//   1. 读当前版本 cur = PRAGMA user_version
//   2. cur > target → 拒绝启动（数据库比二进制新，防危险降级）
//   3. 按版本升序执行所有 version > cur 的 step，每步一个事务：
//        BEGIN → Up(db) → PRAGMA user_version = step.Version → COMMIT
//        任一步失败 → ROLLBACK → 返回错误 → 启动退出（沿用 M1 启动自检约定）
//   4. 返回本次实际执行的步骤列表，供调用方打日志与写审计
func applyMigrations(db *sql.DB) ([]appliedStep, error)
```

要点：
- **每步一事务**：`PRAGMA user_version = N` 放在同一事务内，与 DDL 原子生效，杜绝"结构改了版本没记"。
- **失败即退出**：不吞错误、不降级启动（`database.Open` 已有的行为不变）。
- **步骤列表可观测**：`database.Open` 返回 `(*sql.DB, AppliedSteps, error)` 或把结果写入包级 `lastApplied`，`main.go` 在启动日志中打印 `schema v1 → v3（applied: admin_user_role, api_key_hash）`。
- **不动 `migrations` 变量**：`upBaselineTables` 内部就是原 `migrations` 的循环执行，v1 step 只是把它包起来，保证存量库（已建表、未写版本）也能平滑升到 v1。

### 3.3 危险降级保护（红线，v2 生效）

```
cur := PRAGMA user_version
if cur > targetSchemaVersion() {
    return fmt.Errorf("数据库 schema 版本 v%d 高于当前二进制支持的 v%d；"+
        "请升级二进制，或用备份恢复数据库（旧二进制无法正确读取新版结构）", cur, targetSchemaVersion())
}
```

这条拦截把 F-021 的「加密库被旧二进制打开 → 认证全断」从**运行期故障**降级为**启动期明确报错**。测试用例：`TestRefuseDowngradeBinary`。

### 3.4 `-migrate-only` 运维开关

新增 flag：只做迁移与自检，打印结果后退出（exit code 0/1），不监听端口。

| 场景 | 命令 |
|------|------|
| 发布前预演迁移 | `authcenter -data-dir ./data -migrate-only` → 打印 `schema v1 → v3，applied: ...` |
| 迁移失败不启服务 | 退出码非 0，服务未启动，运维可安全回滚二进制与数据 |

`config.Config` 加 `MigrateOnly bool`（默认 false）；`main.go` 在 `database.Open` 之后、admin 初始化之前判断返回。**注意**：`-migrate-only` 只跑 DDL 迁移，**不跑**后台 job（F-021 的 `key_hash` 回填）——那属于运行期维护。

## 4. 维护任务框架（`internal/service/maintenance.go`）

F-019 的审计清理与 F-021 的 `key_hash` 回填都是「分批 + 可中断 + 不阻塞启动」的同类任务，抽一个共用框架，避免两套 ticker 与两套互斥逻辑。

```go
// Job 维护任务：一个可重复执行、可分批、可被手动触发的后台任务。
type Job interface {
	Name() string                       // 日志与审计用，如 "audit_cleanup" / "key_hash_backfill"
	Interval() time.Duration            // 定时周期（0 = 不自动执行，只允许手动）
	Run(ctx context.Context) (Result, error)  // 返回 { Affected int64, Detail map[string]any }
}

// MaintenanceRunner 维护任务运行器：
//   - 单一 ticker，按各 Job.Interval 触发（间隔不同则各自计时器）；
//   - 每个 Job 独立 TryLock 互斥（手动与定时撞车时后者跳过并记日志）；
//   - 复用 main 的 signal.NotifyContext ctx，随优雅关闭停止；
//   - 失败只 logger.Error + 写审计，绝不影响 HTTP 服务。
type MaintenanceRunner struct { ... }

func (r *MaintenanceRunner) Register(j Job)
func (r *MaintenanceRunner) Start(ctx context.Context)
func (r *MaintenanceRunner) RunNow(ctx context.Context, name string) (Result, error)  // 手动触发
```

**落位影响**：
- F-019《01》§4.1/§4.2 改为：`AuditRetentionService` 实现 `Job` 接口（`Name()="audit_cleanup"`，`Interval()=audit_cleanup_interval_hours`），心跳幂等逻辑移入 `Run` 开头；ticker 由 `MaintenanceRunner` 统一托管。手动触发仍走 `POST /api/v1/settings/audit/cleanup-now`（handler 调 `RunNow`）。
- F-021《03》的 `key_hash` 回填实现为 `Job`（`Name()="key_hash_backfill"`，`Interval()=0`，只手动/一次性），详见《03》§4.7 修订。

`main.go` 装配顺序（`signal.NotifyContext` 之后）：

```go
maint := service.NewMaintenanceRunner(st, auditSvc, logger)
retentionSvc := service.NewAuditRetentionService(st, auditSvc, logger) // Job
backfillSvc := service.NewKeyHashBackfillService(st, auditSvc, logger) // Job（F-021）
maint.Register(retentionSvc).Register(backfillSvc)
maint.Start(ctx)
```

## 5. 启动流程修订（含 F-021 回填移出启动路径）

```
database.Open(dataDir)
  ├ PRAGMA（WAL / busy_timeout / foreign_keys）
  ├ applyMigrations：v1 → target（DDL + 版本号，每步一事务）
  └ 返回 applied 列表
main.go
  ├ 打印 schema 版本跃迁日志
  ├ -migrate-only ? 直接退出（exit 0/1）: 继续
  ├ EnsureOwnerBackfill 已由 v3 step 承担 → main 中删除该调用（避免两处写 role）
  ├ ensureJWTSecret
  ├ ensureKeyEncryptionReady（**只做 DDL 后的状态自检，不再回填 hash**）
  ├ 装配 service
  ├ signal.NotifyContext
  ├ MaintenanceRunner.Start(ctx)  ← key_hash 回填在此后台跑
  └ HTTP 服务启动
```

> F-020 的 `EnsureOwnerBackfill` 调用点需从 `main.go` 移入 v3 迁移 step（同一事务），避免"迁移与回填两处维护"的分裂。

## 7. 迁移步骤清单（与 F-020/F-021 的对应）

| 版本 | 名称 | 内容 | 事务 | 数据量影响 |
|------|------|------|------|-----------|
| v1 | `baseline_tables` | 现有 6 张表 `CREATE TABLE IF NOT EXISTS` + 写 `user_version=1` | 是 | 无（存量库直接空跑） |
| v2 | `api_key_hash` | `api_key` +`key_hash`/`key_value_enc` + `idx_key_hash` 唯一索引 | 是 | 索引构建扫全表（当前量级 <1ms） |
| v3 | `admin_user_role` | `admin_user` +`role`/`force_password_change`/`updated_at` + owner 回填（1 行） | 是 | 极小 |
| — | `key_hash_backfill`（**非迁移 step**） | `key_hash` 数据回填 | 分批提交 | 由后台 job 承担，见《03》 |

**v2 的索引与 NULL**：`CREATE UNIQUE INDEX` 允许多行 NULL，因此**先建索引后回填是安全的**；若回填阶段出现重复 hash（40 位随机串碰撞概率可忽略），会触发 UNIQUE 冲突并使该批回滚——job 需捕获后停止并告警，不静默跳过。

## 10. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 迁移失败导致库半升级 | 每 step 一事务 + 版本号同事务提交 → 要么全做要么全不做；SQLite DDL 事务性良好 |
| 旧二进制误跑新库 | §3.3 启动期硬拦截；错误信息直接给出处置建议 |
| 版本号被误改（手滑把某 step 删了） | 版本号只决定"该不该跑"，step 内部幂等 → 跳版本最多导致回填延后，不会破坏数据；审计 `system.schema_migrated` 记录实际 applied 列表便于发现 |
| 存量库首次启动写 v1 时并发 | 单实例单连接，`Open` 内串行，无竞态 |
| 回滚 | 迁移只加列/加索引，**新列对旧二进制透明**；除 F-021 加密启用外，旧二进制可读新库（但 v>target 时会被 §3.3 拦下，属预期行为：要么换回新二进制，要么用备份恢复） |
